# MoodWave 情绪记录与治愈音乐 V2 优化方案

> 版本：V1.0  
> 状态：方案稿  
> 目标页面：`/mood`、`/music`，兼顾 `/analytics` 的入口关系  
> 核心原则：不推倒现有实现，在当前 Web 端代码基础上，把记录情绪和治愈音乐做成更有差异化、可展示、可继续开发的作品集模块。

---

## 1. 背景与机会

### 1.1 外部机会：网易云音乐「AI 情绪调音师」

网易云音乐在 2026 年 6 月上线「AI 情绪调音师」，其核心方向是让 AI 自动识别歌曲主导情绪，并生成专属音效参数与视觉氛围，实现“一曲一情绪”的沉浸式听感体验。

公开报道中提到的关键能力包括：

- 从频谱、动态、空间、节奏、人声、乐器等声学维度解析歌曲特征。
- 覆盖甜蜜、浪漫、治愈、孤独、悲伤、深情等 15 类情绪标签。
- 使用 EQ、混响、延迟、立体声增强、压缩器等参数形成专属调音方案。
- 将响度、高频、人声、节奏、声场、空间、层次做成可视化维度，并匹配情绪动画。

参考：

- 中国日报转载报道：https://ex.chinadaily.com.cn/exchange/partners/82/rss/channel/cn/columns/snl9a7/stories/WS6a292134a310942cc49b10e0.html
- 新浪科技报道：https://finance.sina.com.cn/tech/roll/2026-06-10/doc-iniaxkrq2673079.shtml

### 1.2 MoodWave 的差异化机会

网易云音乐的切入点是「理解歌曲的情绪，再调音」。MoodWave 更适合切入另一端：

> 先理解用户此刻的身体、情绪和需求，再推荐或生成一段适合 TA 的治愈音乐。

这能让 MoodWave 从普通情绪日记升级为：

- 情绪输入更轻：用户不需要一开始判断“我是焦虑还是难过”。
- 情绪理解更细：用身体体感、呼吸、文字、语音、历史记录形成情绪向量。
- 音乐推荐更准：不是只按 6 类情绪选歌，而是按“用户此刻需要什么感受”给音乐处方。
- 作品集叙事更强：4 月 PCG 项目已经做过情绪音乐 MVP，现在可基于行业新功能做二次产品升级。

## 2. 当前代码基线

### 2.1 情绪记录页 `/mood`

当前实现文件：`frontend/src/app/mood/page.tsx`

现状：

- 三步流程：心情/标签、强度滑块 + 文图音、AI 分析结果。
- Step 1 让用户先选择 6 类情绪和标签。
- Step 2 用 1-10 强度滑块，再填写文字、图片、语音。
- Step 3 调用 AI 分析并保存记录，结果页提供「播放治愈音乐」入口。
- 右侧只有“当前记录预览”和“灵音会先看这些线索”。

问题：

- 首屏仍是传统「选择情绪 + 强度」模型，和多数 mood tracker 同质化。
- 用户需要先总结自己的情绪，表达压力较高。
- 文图音都被放在记录流程中段，信息密度高，但入口不够轻。
- 历史趋势、最近记录、连续打卡等信息在 `/analytics`，没有前置到记录页。

### 2.2 治愈音乐页 `/music`

当前实现文件：`frontend/src/app/music/page.tsx`

现状：

- 已有真实音频曲库、播放进度、收藏、随机、重置、分享占位。
- 支持 Web Audio AnalyserNode 获取频谱和波形数据。
- Canvas 已能绘制渐变背景、音频 ribbon、粒子、orb、环形波形。
- 支持 BPM 播放速度调节。
- 已接入 `CompanionAvatar`，用作“灵音伙伴的听后感”。
- 推荐歌曲来自 `backend/src/services/music_catalog.py`，接口为 `/api/music/recommend`。

问题：

- 推荐逻辑仍主要基于 `mood_type`，个性化程度有限。
- 调节只有 BPM，和网易云提到的“多维调音参数”相比表达力不足。
- 灵音伙伴在音乐页存在感偏弱，更像辅助卡片，不是音乐房舞台的一部分。
- AI 生成音乐还没有形成用户可操作的创作入口。

### 2.3 情绪趋势页 `/analytics`

当前实现文件：`frontend/src/app/analytics/page.tsx`

现状：

- 已有月度趋势折线图、情绪分布、热力日历、AI 月度洞察、全部记录、编辑/删除。
- 能从 `/api/analytics/weekly`、`/api/analytics/summary`、`/api/moods` 拉取数据。

判断：

- `/analytics` 不需要删除。
- 但它不适合作为高频一级核心路径。
- 建议降级为“完整历史与编辑中心”，把精简趋势前置到 `/mood` 首页。

## 3. V2 产品目标

### 3.1 核心目标

把 MoodWave 的核心路径改成：

```text
打开 /mood
  -> 看到今日情绪总览和最近趋势
  -> 用身体体感低压力记录
  -> AI 生成情绪向量和音乐目标
  -> 进入 /music 接收音乐处方或生成专属音乐
```

### 3.2 成功标准

- 用户不需要先选择“开心/悲伤/焦虑”等抽象情绪，也能完成记录。
- 主记录流程在 30 秒内可完成。
- 记录后能生成兼容旧系统的 `mood_type/intensity`，并额外产出 `emotion_vector`。
- 音乐页能解释“为什么推荐这首/这组参数”。
- 作品集展示时能讲清：MoodWave 不是简单情绪日记，而是“情绪理解 -> 音乐处方 -> 治愈陪伴”的闭环。

### 3.3 信息架构决策

V2 不新增“身体体感记录”一级导航。身体体感、意象词和快速记录都属于 `/mood` 情绪录入内部的不同模式。

一级导航保持：

```text
/dashboard   首页
/mood        情绪录入
/analytics   情绪趋势
/music       治愈音乐
/companion   灵音伙伴
/discovery   解忧角
/profile     个人主页
```

`/mood` 内部使用 query mode 切换：

```text
/mood                 情绪记录总览 overview
/mood?mode=body       身体体感记录
/mood?mode=imagery    意象词记录
/mood?mode=quick      快速文字/语音记录
```

这样导航不会膨胀，也符合产品逻辑：身体体感不是独立业务模块，而是情绪录入的一种低压力输入方式。

## 4. 情绪记录 V2 方案

### 4.1 `/mood` 改为情绪主页

原 `/mood` 直接进入三步记录表单。V2 建议先做成情绪主页，包含四个区域：

1. 今日状态总览
   - 最近一次记录的情绪、日期、简短摘要。
   - 连续记录天数。
   - 今日推荐音乐入口。
   - 灵音伙伴一句今日陪伴。

2. 记录入口
   - 主按钮：`开始体感记录`。
   - 辅助按钮：`意象词记录`、`快速文字记录`、`语音碎碎念`。
   - 不展示情绪曲线入口，曲线放到 V2.1。

3. 精简趋势
   - 最近 7 天小趋势。
   - 本月主导状态。
   - 高频标签。
   - 「查看完整历史」跳转 `/analytics`。

4. 最近记录
   - 复用 `/analytics` 的记录列表逻辑，但只展示最近 3-5 条。
   - 提供补记入口。

### 4.2 记录方式取舍

豆包给的方案不全部进入首版，V2 只采用如下优先级：

| 方案 | V2 状态 | 原因 |
| --- | --- | --- |
| 身体体感映射 | 主推 | 低表达压力、差异化强、和治愈音乐高度相关 |
| 意象词云 | 备选 | 适合偏文艺、抗拒身体图的用户 |
| 快速文字记录 | 备选 | 兼容老用户习惯和极简输入 |
| 情绪曲线 | 暂缓 V2.1 | 更适合长期趋势，首版会增加实现和理解成本 |
| 色彩拾取/场景勾选 | 暂不做 | 可以合并进音乐目标或后续增强，不抢首版焦点 |

### 4.3 身体体感映射：主记录方式

#### 4.3.1 为什么用人物轮廓，不用动物形象

主图使用极简人物半身轮廓，不使用动物形象做身体标记。

原因：

- 身体体感需要准确表达头部、胸口、肩颈、腹部、手部、整体状态。
- 动物形象会让部位映射变含糊，用户可能不确定“点小动物胸口是不是代表我的胸口”。
- MoodWave 的小动物更适合承担陪伴反馈，而不是输入坐标。

#### 4.3.2 页面布局

桌面端：

- 左侧 60%：极简人物半身轮廓。
- 右侧 40%：当前线索、呼吸状态、音乐目标、小动物陪伴反馈。

移动端：

- 上方：人物轮廓。
- 下方：标签选择 bottom sheet。
- 底部固定提交按钮。

#### 4.3.3 可点击区域

只保留 6 个区域，避免医学感和操作负担：

- 头部
- 肩颈
- 胸口
- 腹部
- 手部
- 整体

每个区域是透明热区。默认只显示淡淡轮廓和小光点；选中后出现马卡龙高亮：

- 头部：淡蓝涟漪。
- 胸口：粉橘呼吸光晕。
- 肩颈：薄荷色缓释光。
- 腹部：浅黄暖光。
- 手部：小粒子闪动。
- 整体：人物轮廓外圈柔和呼吸。

实现建议：

- 首版使用 SVG，不使用 Canvas。SVG 更适合可点击热区、hover/focus 状态、响应式缩放和无障碍标签。
- 每个部位由两层元素组成：可视轮廓层 + 透明热区层。透明热区面积略大于视觉区域，移动端更易点中。
- 每个热区使用 `button` 语义或带 `role="button"` 的可聚焦元素，支持键盘 `Enter/Space` 选择。
- 点击后不跳转页面，而是在该部位附近打开轻量浮窗。

部位与情绪关联：

| 部位 | 常见情绪线索 | 推荐解释方向 |
| --- | --- | --- |
| 头部 | 思绪杂乱、脑子停不下来、发沉 | 焦虑、内耗、疲惫 |
| 肩颈 | 紧绷、僵硬、沉重 | 压力、紧张、长期疲劳 |
| 胸口 | 发闷、发慌、堵得慌、沉重 | 焦虑、压抑、悲伤 |
| 腹部 | 发紧、发空、灼烧感 | 焦虑、愤怒、烦躁 |
| 手部 | 发冷、发麻、想攥紧 | 紧张、愤怒、无力 |
| 整体 | 疲惫、麻木、慌乱、轻盈 | 整体能量水平和安抚需求 |

#### 4.3.4 解压式点击反馈

身体体感记录不是普通表单，需要让用户感觉“身体线索被释放和接住”。反馈分四层实现。

1. 触摸/悬停预览
   - 桌面 hover 时部位出现低透明光晕。
   - 旁边出现短提示：`这里有感觉吗？`
   - 移动端第一次点击即展示提示。

2. 点击后的颜色与动效
   - 头部：淡蓝涟漪向外扩散。
   - 胸口：粉橘色呼吸光圈。
   - 肩颈：薄荷色缓慢散开。
   - 腹部：暖黄色柔光。
   - 手部：小粒子松开。
   - 整体：人物轮廓外圈柔和呼吸。

3. 点击频率反馈
   - 记录同一部位的点击次数和简单停留时间，用于前端即时反馈。
   - 连续点胸口 3 次：`这里好像很需要被照顾，我们先把呼吸放慢一点。`
   - 快速点多个区域：`身体给了很多信号，先选最明显的 1-2 个就好。`
   - 首版该数据只用于前端提示，不强制入库。

4. 部位浮窗
   - 点击部位后出现小云朵浮窗，位置跟随部位。
   - 例如胸口浮窗：`胸口现在更像？`，选项为 `发闷`、`发慌`、`堵得慌`、`沉重`、`舒展`。
   - 选中标签后进入右侧“已选线索” chips。

#### 4.3.5 表情辅助控件优先级

可以增加表情辅助，但不做复杂捏脸系统。

优先级：

| 优先级 | 内容 | 是否进入首版 |
| --- | --- | --- |
| P0 | 身体区域 + 标签 + 呼吸 + 音乐目标 | 是 |
| P1 | 点击频率/动态反馈 | 可做轻量版 |
| P2 | 表情辅助控件：嘴角、眼睛、眉毛几个预设状态 | 后续增强 |
| P3 | 真正捏脸式自由编辑 | 暂不做 |

推荐 P2 形式：

- 嘴巴：上扬、平直、下垂、抿住。
- 眼睛：放松、疲惫、紧张、想哭。
- 眉毛：舒展、皱起、低垂。

它只作为身体体感后的辅助线索，不替代身体记录。

#### 4.3.6 标签选择

用户点击区域后，弹出该区域标签。

规则：

- 每个区域最多选 2 个标签。
- 全部区域合计最多 6 个标签。
- 标签可随时删除。
- 用户可以不选具体区域，直接点快捷组合。

标签词库：

| 区域 | 标签 |
| --- | --- |
| 头部 | 发沉、发胀、思绪杂乱、脑子停不下来、空空的 |
| 胸口 | 堵得慌、发闷、发慌、沉重、舒展 |
| 肩颈 | 僵硬、紧绷、沉重、放松 |
| 腹部 | 发紧、发空、灼烧感、安稳 |
| 手部 | 发冷、发麻、想攥紧、放松 |
| 整体 | 疲惫、浮躁、麻木、慌乱、无力、轻盈 |

#### 4.3.7 快捷组合

首版默认提供 3 个快捷组合：

- 脑子停不下来：头部 `思绪杂乱`、头部 `脑子停不下来`、呼吸 `shallow`。
- 胸口闷闷的：胸口 `发闷`、肩颈 `紧绷`、呼吸 `shallow`。
- 全身没电：整体 `疲惫`、整体 `无力`、头部 `发沉`。

额外提供一个“一键不确定”：

- 说不上来，只是有点累。
- 说不上来，只是有点乱。
- 说不上来，只是有点空。

#### 4.3.8 呼吸状态

体感标签下方增加呼吸单选：

- 急促
- 浅浅的
- 平稳
- 舒展

它不直接等于情绪，但用于校准焦虑、紧绷、松弛等维度。

#### 4.3.9 音乐目标

记录完成前，增加一句轻量问题：

> 你希望音乐现在帮你做什么？

选项：

- 慢慢平复
- 放松助眠
- 给一点力气
- 安全释放
- 只是陪着我

这比单纯调 BPM 更能决定音乐推荐方向。

### 4.4 意象词记录：备选模式

定位：

- 不作为首屏默认。
- 入口放在体感记录页顶部或 `/mood` 首页辅助按钮。
- 适合“不想看身体图，只想凭感觉选词”的用户。

交互：

- 不做复杂拖拽，首版用点击收集。
- 一次展示 18-24 个词。
- 最多选 5 个。
- 支持刷新词库。

词库示例：

- 压抑：乌云、死水、密闭房间、浓雾、低气压。
- 疲惫：慢流沙、没电灯泡、负重背包、阴天傍晚。
- 烦躁：蜂鸣、乱风、碎纸屑、噪点雪花。
- 治愈：晚风、湖面、暖阳、软云、溪流、星空。
- 目标：想安静、想被安抚、想振奋、想慢慢平复。

### 4.5 文图音：补充输入

现有组件：

- `MoodMediaUpload`
- `MoodVoiceRecorder`

V2 不重写，改交互位置：

- 默认折叠。
- 标题为：`补充一点小细节（选填）`。
- 用户完成体感/意象记录后自动轻提示展开。
- 文本限制建议从现有 700 字调整为 UI 提示 150-300 字，但后端不强制变更。
- 图片和语音仍进入 AI 分析。

## 5. 情绪理解策略

### 5.1 首版不做模型微调

V2 首版不做微调，采用：

```text
结构化输入
  + LLM 情绪推理
  + 规则校准
  + 历史记录上下文
  + 用户反馈记忆
```

不微调的原因：

- 当前没有足够高质量标注数据。
- 情绪识别高度主观，直接训练容易过拟合。
- 产品现阶段更需要可解释的输入结构、推荐解释和反馈闭环。
- 作品集阶段展示“产品闭环 + 工程架构 + 后续学习路线”比直接训练一个不稳定模型更有价值。

### 5.2 多模态线索分工

| 输入 | 首版作用 |
| --- | --- |
| 身体体感 | 判断紧绷、焦虑、疲惫、低落、松弛等基础向量 |
| 呼吸状态 | 校准焦虑/平静/安抚需求 |
| 意象词 | 增强情绪氛围和音乐生成 prompt |
| 文字 | 分析情绪原因、事件背景、人际/学习/工作压力 |
| 语音转写 | 补充表达内容，捕捉碎碎念中的真实情绪 |
| 语音基础特征 | 辅助判断语速、停顿、音量变化，不做复杂声学模型 |
| 图片 | 补充场景氛围，例如截图杂乱、夜景、风景、色调 |
| 历史记录 | 判断近期趋势、连续低落/焦虑、常见触发场景 |

### 5.3 情绪向量

首版输出不只保存 6 类情绪，还要规划多维向量：

```ts
type EmotionVector = {
  anxiety: number
  fatigue: number
  sadness: number
  anger: number
  calm: number
  joy: number
  soothing_need: number
  activation_need: number
}
```

示例：

```json
{
  "mood_type": "anxious",
  "intensity": 7,
  "emotion_vector": {
    "anxiety": 0.82,
    "fatigue": 0.46,
    "sadness": 0.24,
    "anger": 0.12,
    "calm": 0.18,
    "joy": 0.08,
    "soothing_need": 0.88,
    "activation_need": 0.22
  }
}
```

### 5.4 语音理解策略

首版继续使用 ASR 转写，保留现有 `voice_text`。

新增规划字段：

```ts
type VoiceFeatures = {
  duration: number
  speech_rate?: number
  pause_ratio?: number
  volume_variation?: number
  short_sentence_ratio?: number
}
```

实现优先级：

1. 先记录语音时长和转写文本。
2. 再做轻量特征：说话时长、文字长度、平均句长、停顿粗估。
3. 后续再考虑 pitch、energy、tempo 等声学特征。
4. 不在首版训练语音情绪模型。

### 5.5 个性化校准

用户级校准比训练大模型更适合当前阶段。

可记录的反馈：

- 用户是否收藏推荐音乐。
- 用户是否跳过某首音乐。
- 用户是否重新生成陪伴语。
- 用户是否修正 AI 判断的情绪。
- 用户偏好纯音乐、人声、自然声、钢琴、白噪声等。

这些反馈用于调整推荐权重，不需要微调基础模型。

## 6. 微调与学习路线

### 6.1 阶段判断

| 阶段 | 是否微调 | 目标 |
| --- | --- | --- |
| MVP/作品集阶段 | 不微调 | 做出体验闭环和可解释推荐 |
| 数据积累阶段 | 不微调或轻量分类器 | 收集匿名样本和用户反馈 |
| 研究学习阶段 | 可做小实验 | 学习文本分类、声学特征、LoRA |
| 产品成熟阶段 | 视数据量决定 | 多标签情绪模型或音乐生成模型 |

### 6.2 数据怎么收集

后续如果要微调，不按“每类情绪一个模型”收集数据，而是每条样本保存多维标签。

一条样本包含：

- `body_sensations`
- `breath_state`
- `imagery_words`
- `note`
- `voice_text`
- `voice_features`
- `history_summary`
- AI 初判
- 用户修正
- 用户选择/收藏/跳过的音乐
- 最终 `emotion_vector`

更推荐的标注目标：

- 焦虑
- 疲惫
- 低落
- 愤怒
- 平静
- 愉悦
- 安抚需求
- 激活需求

不推荐只标：

- 开心
- 平静
- 焦虑
- 愤怒
- 悲伤
- 平淡

原因：单标签太粗，无法支撑音乐处方。

### 6.3 Mac 上能做什么

Mac 适合：

- 文本情绪分类小实验。
- 语音基础特征提取实验。
- 小规模 LoRA 学习。
- 数据清洗和标注工具开发。
- prompt 对比和评估脚本。

Mac 不适合：

- 大规模音频情绪识别训练。
- 音乐生成模型从头训练。
- 大模型音乐生成微调。

建议：

- 训练类任务用 Colab、AutoDL、腾讯云 GPU 或其他云 GPU。
- 本地用 Mac 做产品、前端、数据结构、评估工具、轻量实验。

### 6.4 可学习方向

- 文本情绪识别：BERT、中文 RoBERTa、小型 LLM LoRA。
- 语音情绪识别：pitch、energy、tempo、pause、spectrogram。
- 音乐情绪建模：valence/arousal 情绪二维空间。
- 音乐生成：MusicGen、AudioLDM、Stable Audio 类开源模型。
- 生成式音乐评价：结构一致性、听感舒适度、循环可听性、版权安全。

## 7. 数据与接口规划

### 7.1 兼容现有数据模型

### 7.2 新增扩展字段

建议新增字段首版先用 JSON 字符串存储，保证本地 SQLite 与服务器 PostgreSQL 都能兼容；生产数据库后续再迁移为 PostgreSQL JSONB。

```ts
type MoodEntryV2Extension = {
  input_mode: "classic" | "body_map" | "imagery_cloud"
  body_sensations?: Array<{
    part: "head" | "shoulder_neck" | "chest" | "abdomen" | "hands" | "whole"
    labels: string[]
  }>
  imagery_words?: string[]
  breath_state?: "rapid" | "shallow" | "normal" | "deep"
  voice_features?: VoiceFeatures
  music_goal?: "calm_down" | "sleep" | "energize" | "release" | "accompany"
  emotion_vector?: EmotionVector
}
```

数据库兼容策略：

- 本地开发默认可能使用 SQLite，服务器/docker 使用 PostgreSQL。
- 当前项目没有 Alembic，先延续 `backend/src/db/database.py` 的 `_ensure_runtime_columns()` 轻量补列策略。
- 新增 V2 字段首版统一使用 `TEXT DEFAULT ''`，内容为 JSON 字符串，避免 SQLite/PostgreSQL 类型差异。
- 后续生产稳定后，再为 PostgreSQL 单独迁移为 JSONB，并补索引。
- 不把服务器数据库密码写入代码；服务器使用 CloudBase 环境变量或 `.env` 注入 `DATABASE_URL` / `DB_PASSWORD`。

### 7.4 对象存储与音频资产管理

结论：

- MVP / 本地作品集阶段可以先不接 COS。
- 上线、真实用户上传、AI 生成音乐阶段建议接腾讯云 COS。

需要 COS 的原因：

- 用户上传图片、语音、未来短视频不能长期依赖本地服务器目录。
- AI 生成音乐通常是 mp3/wav 文件，体积较大，需要稳定对象 URL。
- Docker 容器本地文件不适合长期持久化，迁移、重启、扩容都不稳定。
- 音频播放需要稳定访问链路，COS + CDN 比后端直接传文件更合适。
- 作品集展示时，COS 能体现“上传素材、生成资产、播放访问、资产管理”的完整工程链路。

分阶段方案：

1. 本地原型阶段
   - 保留当前上传接口和 `frontend/public/audio/music-room/` 本地曲库。
   - 图片、语音、AI 音乐生成结果可以先存本地或使用 mock URL。
   - 数据库先记录 URL 和来源字段，避免后续迁移时重构业务逻辑。

2. 腾讯云 COS 阶段
   - 图片、语音、AI 生成音乐统一上传 COS。
   - 后端负责生成 object key、上传、返回访问 URL。
   - 数据库只保存 URL、文件类型、大小、来源、生成参数。
   - 公开音乐可走 CDN；私人日记素材建议使用签名 URL 或权限控制。

3. AI 音乐资产管理阶段
   - AI 生成结果存 COS。
   - 保存生成 prompt、情绪向量、音乐目标、模型 provider、模型名、时长、版权/许可状态。
   - 用户可以收藏、复用、删除生成音乐。

建议新增资产字段：

```ts
type GeneratedAudioAsset = {
  id: string
  user_id: number
  mood_entry_id?: number
  storage_provider: "local" | "tencent_cos"
  audio_url: string
  object_key?: string
  mime_type: "audio/mpeg" | "audio/wav"
  file_size?: number
  duration?: number
  source: "catalog" | "ai_generated" | "procedural"
  model_provider?: "gemini_lyria" | "stable_audio" | "musicgen" | "other"
  model_name?: string
  prompt?: string
  emotion_vector?: EmotionVector
  music_goal?: string
  license_status?: "user_private" | "public_safe" | "unknown"
  created_at: string
}
```

## 8. 治愈音乐 V2 方案

### 8.1 页面定位

`/music` 从“播放器”升级为“治愈音乐工作台”：

- 先解释此刻为什么推荐这组音乐。
- 再播放音乐。
- 同时允许用户调节“治愈方向”。
- 最后提供 AI 生成专属音乐入口。

### 8.2 首屏结构

保留当前大 Canvas 舞台，但做三点调整：

1. 灵音伙伴进入主舞台
   - 当前 `CompanionAvatar` 只在听后感卡片出现。
   - V2 让 `CompanionPetOrb` 出现在 Canvas 前景或舞台侧边。
   - 伙伴随播放状态轻微呼吸、靠近、发光。

2. 音乐处方说明
   - 当前显示 mood 和 intensity。
   - V2 改为：`你现在更需要：慢慢平复 / 放松助眠 / 给一点力气`。
   - 显示推荐理由：例如“胸口发闷 + 呼吸浅，先选低节奏密度和更大空间感”。

3. 调音面板替代单一 BPM
   - BPM 仍保留，但不作为唯一调节项。
   - 增加空间感、明亮度、低频包裹、节奏密度、自然声比例、纯音乐/人声倾向。

### 8.3 音乐推荐升级

当前：

```text
mood_type -> MUSIC_RECOMMENDATIONS[mood_type]
```

V2：

```text
current mood entry
  + emotion_vector
  + music_goal
  + recent 7/30 day history
  + user profile
  + favorite/skip feedback
  -> music prescription
```

推荐理由示例：

- 焦虑高 + 呼吸浅：低节奏密度、稳定脉冲、自然声占比更高。
- 疲惫高 + 激活需求低：低频包裹、柔和长音、避免高频刺激。
- 低落高 + 安抚需求高：暖色和弦、缓慢上行旋律、少量明亮点。
- 愤怒高 + release 目标：保留低频力量，但减少刺耳高频，节奏从紧到松。

### 8.4 AI 生成音乐入口

首版建议接 Gemini/Lyria 3 或同级官方音乐生成 API。

定位：

- 不是让用户从零写 prompt。
- 用户选择模板，系统根据情绪向量自动填充 prompt。

模板：

- 睡前慢慢放松。
- 先把焦虑降下来。
- 给低落一点暖光。
- 安全释放愤怒。
- 陪我专注 20 分钟。

生成 prompt 示例：

```text
Create a 45-second seamless instrumental ambient loop for emotional soothing.
Mood: anxious but tired.
Goal: calm down and feel safe.
Instruments: soft piano, warm pad, subtle rain texture.
Avoid: harsh percussion, sudden transitions, bright aggressive synths.
Tempo: slow and steady.
Texture: spacious, gentle, breathable.
```

参考：

- Lyria 3 文档：https://ai.google.dev/gemini-api/docs/music-generation
- Lyria 3 支持文本和图片生成 44.1kHz 立体声音频。
- Clip 适合 30 秒 loop/previews，Pro 适合完整歌曲。

### 8.5 Tone.js 的定位调整

Tone.js 不再作为主听感方案。

保留用途：

- 本地兜底。
- 呼吸节拍。
- 快速试听草稿。
- 网络失败时的低成本陪伴音。

主听感：

- 本地版权安全曲库。
- AI 生成音频。
- 后续可接更专业音乐生成服务。

### 8.6 可视化优化

当前 Web Audio + Canvas 已经可继续增强。

V2 重点：

- 让情绪向量决定视觉 preset。
- 让音频频谱决定实时动态。
- 让灵音伙伴表达陪伴反馈。

映射示例：

| 情绪向量 | 视觉 |
| --- | --- |
| anxiety 高 | 粒子从紧密线团逐渐散开 |
| fatigue 高 | 低速漂浮、暖色呼吸、减少闪烁 |
| sadness 高 | 下沉雾面、缓慢上浮微光 |
| anger 高 | 暖色低频脉冲，边缘逐渐变柔 |
| calm 高 | 水波、浅海、圆形扩散 |
| joy 高 | 小星点、轻快弹跳、明亮但不刺眼 |

后续高阶版：

- 引入 Three.js。
- 做 3D 治愈房间或漂浮岛屿。
- 参考：https://tympanus.net/codrops/2025/06/18/coding-a-3d-audio-visualizer-with-three-js-gsap-web-audio-api/

## 12. 风险与边界

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 体感记录被误解成医学诊断 | 用户可能把身体体感当成健康判断 | 明确文案：这是情绪记录，不是医疗诊断 |
| 选择过多导致复杂 | 标签、目标、补充输入太多 | 首屏只放 6 个区域和少量标签 |
| AI 情绪判断不准 | 情绪主观性强 | 保留用户修正入口和规则兜底 |
| 音乐生成成本高 | 外部 API 可能收费或排队 | 本地曲库 + Tone.js 兜底 |
| 版权风险 | AI 音乐和外部曲库要注意授权 | 使用官方 API、保留来源和许可记录 |
| 文件存储不可持续 | 本地文件不适合保存用户上传和 AI 生成音频 | 上线阶段接腾讯云 COS，数据库只存 URL 和元数据 |
| 微调投入过大 | 数据不足时训练收益低 | 首版不微调，先做反馈闭环 |

---

## 13. 结论

V2 不应该追求“功能都上”，而应该聚焦一个清晰的产品判断：

> 身体体感是主入口，意象词是备选，情绪曲线后置；先把用户状态理解细，再让音乐推荐和生成变准。

这条路线能让 MoodWave 从普通情绪记录产品升级为有差异化的 AI 情绪音乐平台，也能为后续投递网易云音乐相关岗位提供更完整的作品集故事：

- 你做过情绪音乐 MVP。
- 你能基于竞品新功能做产品拆解。
- 你能把真实代码现状转成可落地的 V2 方案。
- 你理解 AI 音乐、情绪识别、前端交互和数据闭环之间的关系。

## 14. 算法学习与深度优化资料

本节用于后续深入学习 AIGC 音乐生成、音乐可视化原理和微调策略。建议学习顺序是：

```text
先理解音频表示
  -> 再看文本/图像/视频到音乐生成
  -> 再看 Web Audio 可视化
  -> 最后做 LoRA/微调小实验
```

### 14.1 AIGC 音乐生成论文路线

#### A. MusicGen：文本/旋律可控音乐生成

论文：Simple and Controllable Music Generation  
链接：https://arxiv.org/abs/2306.05284  
代码与模型：https://github.com/facebookresearch/audiocraft

适合学习：

- 音乐如何被压缩成离散 audio tokens。
- EnCodec / RVQ 音频 tokenizer 的作用。
- 单阶段 Transformer 如何生成音乐。
- 文本条件和旋律条件如何控制输出。

对 MoodWave 的启发：

- 如果后续做本地或云端开源音乐生成，MusicGen 是最适合入门的路线。
- 可以先用 prompt 生成短音乐，再研究 LoRA 或风格适配。

#### B. AudioLDM：潜空间扩散生成音频

论文：AudioLDM: Text-to-Audio Generation with Latent Diffusion Models  
链接：https://arxiv.org/abs/2301.12503  
项目页：https://audioldm.github.io

适合学习：

- 文本到音频为什么常用 latent diffusion。
- CLAP 音频-文本对齐表示怎么辅助生成。
- 音频风格迁移、inpainting、super-resolution 的基本思路。

对 MoodWave 的启发：

- MoodWave 的治愈音乐不一定只生成“完整歌曲”，也可以生成自然声、氛围音、呼吸声、雨声底纹。
- AudioLDM 类模型适合学习“声音纹理”和“音乐氛围”的生成。

#### C. Stable Audio / Stable Audio Open：开放权重音乐生成

论文：Stable Audio Open  
链接：https://arxiv.org/abs/2407.14358  
Stability AI 介绍：https://stability.ai/news-updates/stable-audio-open-research-paper  
Hugging Face：https://huggingface.co/stabilityai/stable-audio-open-1.0

适合学习：

- 44.1kHz 立体声生成模型的基本结构。
- autoencoder + 文本编码器 + diffusion transformer 的组合。
- 开放权重模型如何作为研究基线。

对 MoodWave 的启发：

- 如果未来要做“可解释、可微调”的音乐生成研究，Stable Audio Open 比闭源 API 更适合学习。
- 注意版权和训练数据许可，作品集里要写清楚素材来源。

#### D. Lyria 3：工业级 API 生成音乐

文档：https://ai.google.dev/gemini-api/docs/music-generation  
Google Cloud 介绍：https://cloud.google.com/blog/products/ai-machine-learning/lyria-3-and-lyria-3-pro-on-vertex-ai

适合学习：

- 产品层如何把音乐生成封装成 API。
- Clip 和 Pro 两种生成模式如何对应不同产品场景。
- 文本/图片作为音乐生成条件的交互方式。

对 MoodWave 的启发：

- 首版产品不建议自己训练音乐模型，优先接 Lyria 这类官方 API。
- `Lyria 3 Clip` 适合生成 30 秒治愈 loop，`Lyria 3 Pro` 适合生成完整曲目。

#### E. Riffusion：把音乐当频谱图生成

模型页：https://huggingface.co/riffusion/riffusion-model-v1  
OpenVINO 教程：https://docs.openvino.ai/2023.3/notebooks/241-riffusion-text-to-music-with-output.html

适合学习：

- 音频可以转成 spectrogram 图像。
- 为什么只生成幅度谱还不够，还要重建 phase。
- Griffin-Lim 等相位重建算法的基本作用。

对 MoodWave 的启发：

- 这是理解“视觉和音频之间如何互相转换”的好入口。
- 也能帮助理解音乐可视化为什么常看频谱、波形、能量分布。

### 14.2 CVPR / 视觉到音乐生成资料

#### A. MeLFusion：图像 + 文本生成音乐

论文：MeLFusion: Synthesizing Music from Image and Language Cues using Diffusion Models  
会议：CVPR 2024  
链接：https://openaccess.thecvf.com/content/CVPR2024/papers/Chowdhury_MeLFusion_Synthesizing_Music_from_Image_and_Language_Cues_using_Diffusion_CVPR_2024_paper.pdf

适合学习：

- 如何把图片和文本共同作为音乐生成条件。
- diffusion model 如何用于 music spectrogram 或音频生成。
- 图像情绪、文字 prompt 和音乐之间的跨模态对齐。

对 MoodWave 的启发：

- 用户上传图片后，不只是做图片情绪分析，也可以把图片氛围转成音乐 prompt。
- 例如“夜晚宿舍照片 + 低落体感”生成更贴近当下场景的音乐。

#### B. VidMuse：视频到音乐生成

论文：VidMuse: A Simple Video-to-Music Generation Framework with Long-Short-Term Modeling  
会议：CVPR 2025  
链接：https://openaccess.thecvf.com/content/CVPR2025/html/Tian_VidMuse_A_Simple_Video-to-Music_Generation_Framework_with_Long-Short-Term_Modeling_CVPR_2025_paper.html

适合学习：

- 视频如何提取长短期视觉语义，再生成匹配音乐。
- 视觉节奏、场景情绪和音乐结构如何对齐。
- 大规模 video-music pair 数据集如何构建。

对 MoodWave 的启发：

- 未来如果支持用户上传短视频，MoodWave 可以根据视频氛围生成疗愈 BGM。
- 目前不建议首版实现，但适合作为作品集的长期研究方向。

#### C. Vision-to-Music Survey

综述：Vision-to-Music Generation: A Survey  
链接：https://arxiv.org/html/2503.21254v1  
资料合集：https://github.com/wzk1015/awesome-vision-to-music-generation

适合学习：

- image-to-music、video-to-music、dance-to-music 的整体路线。
- 常见数据集、评估指标、模型结构。
- 视觉转音乐目前的难点：语义对齐、节奏对齐、长期结构、主观评价。

### 14.3 音乐可视化原理资料

#### A. Web Audio API 可视化基础

MDN 文档：https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API/Visualizations_with_Web_Audio_API

重点学习：

- `AnalyserNode`
- `getByteFrequencyData`
- `getByteTimeDomainData`
- FFT size、frequencyBinCount、smoothingTimeConstant
- 频域数据和时域数据分别适合画什么

对当前 `/music` 的直接作用：

- 低频 bass 驱动 orb 呼吸和低频脉冲。
- 中频 mids 驱动波纹和空间层。
- 高频 treble 驱动星点、闪光、细粒子。
- overall energy 控制整体亮度和运动幅度。

#### B. 3D Audio Visualizer 实现案例

文章：Coding a 3D Audio Visualizer with Three.js, GSAP & Web Audio API  
链接：https://tympanus.net/codrops/2025/06/18/coding-a-3d-audio-visualizer-with-three-js-gsap-web-audio-api/

适合学习：

- Three.js 如何接 Web Audio 数据。
- 3D orb 如何随音乐起伏。
- 音频响应视觉如何做得高级但不混乱。

对 MoodWave 的启发：

- 当前先保留 Canvas。
- 高阶版可以把 `CompanionPetOrb + 3D orb + 情绪场景` 结合成 3D 治愈房间。

#### C. 音乐情绪可视化：Valence-Arousal

论文：Emotion-Based Music Visualization for the Hearing Impaired  
链接：https://ojs.aaai.org/index.php/AAAI/article/view/26912/26684

适合学习：

- 为什么 arousal-valence 可以作为音乐与视觉之间的桥。
- arousal 更像能量/激活度，valence 更像正负情绪。
- 如何把音乐情绪转成可视化表情或视觉变化。

对 MoodWave 的启发：

- `emotion_vector` 可以进一步压缩成：
  - valence：愉悦/低落方向。
  - arousal：紧绷/平静方向。
  - soothing_need：安抚需求。
- 可视化不要只按 `mood_type`，而要按连续情绪坐标变化。

#### D. 音乐视频情绪研究

论文：Predicting emotion from music videos: exploring the relative contribution of visual and auditory information to affective responses  
链接：https://arxiv.org/abs/2202.10453

适合学习：

- 音频和视觉对情绪感知的贡献不同。
- arousal 更多受音频影响，valence 更主观，也受视觉影响。

对 MoodWave 的启发：

- 音乐听感决定“身体被带起来还是放下来”。
- 视觉和小动物更适合承担“安全、温柔、被陪伴”的 valence 表达。

### 14.5 推荐学习顺序

第一周：音频基础和可视化

- 看 MDN Web Audio 可视化。
- 在当前 `/music` 里理解 bass/mids/treble/overall 如何影响 Canvas。
- 学 FFT、频域、时域、spectrogram、RMS、pitch、tempo。

第二周：AIGC 音乐生成基础

- 看 MusicGen 论文和 Audiocraft demo。
- 看 AudioLDM 项目页。
- 理解 tokenizer、latent diffusion、CLAP、prompt conditioning。

第三周：产品可落地 API

- 看 Lyria 3 文档。
- 设计 MoodWave 的 5 个音乐生成模板。
- 先不要训练，先做 prompt -> audio -> 保存 -> 播放 -> 反馈闭环。

第四周：微调小实验

- 跑 MusicGen LoRA 或 DreamBoothing 教程。
- 用 10-30 段版权安全音频做风格实验。
- 只做学习验证，不直接放进正式产品。

第五周：情绪与可视化结合

- 看 valence-arousal 音乐可视化论文。
- 把 `emotion_vector` 映射成视觉参数。
- 让用户体感输入影响音乐 prompt 和视觉 preset。

### 14.6 对 MoodWave 最有价值的学习结论

短期最值得做：

- 不训练模型，先接 Lyria/API。
- 自己掌握 prompt 模板、情绪向量、推荐解释、播放反馈。
- 用 Web Audio 把已有音乐做得更“看得见情绪”。

中期最值得做：

- 用户反馈驱动个性化推荐。
- 把图片/文字/体感输入合成音乐 prompt。
- 做音乐处方解释和调音面板。

长期再考虑：

- MusicGen/AudioLDM/Stable Audio 的 LoRA。
- 语音情绪识别轻量模型。
- 图像/视频到音乐生成。
- 3D 治愈音乐房。
