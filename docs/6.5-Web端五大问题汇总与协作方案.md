# 6.5 Web端五大问题汇总与协作方案

## 0. 文档目的

本文档用于汇总当前 Web 端最核心的 5 个问题，并明确后续改版时的：

- 问题定义
- 设计方向
- 前后端分工
- 测试流程
- hook / 提交流程
- 代码审查要求
- 参考来源与适合负责的人

本轮范围仅针对 **Web 端**，不写回 iOS 文档。

---

## 1. 总体执行原则

### 1.1 产品方向

Web 端本轮不追求继续堆功能，而是优先解决：

- 首页第一眼观感不对
- 登录与引导体验不统一
- 登录后首页过挤、角色体系不统一
- 情绪录入交互成本太高、AI 真实性弱
- 音乐页更像播放器，不像情绪可视化空间

### 1.2 设计原则

基于 `moodwave-design` 与当前 Web 现状，本轮统一遵循：

- 可爱治愈风，不走赛博重感路线
- 一屏只做一件主事
- 首屏强调主视觉，不堆文字
- 角色体系统一，不混用多套风格
- Web 端优先适配桌面浏览体验，不机械照搬移动端
- 可视化与动态效果要轻，不牺牲流畅度

### 1.3 协作边界

- **前端改版由 Codex 负责**
  - 页面布局
  - 视觉重构
  - 交互优化
  - 前端状态反馈
  - 角色形象落位
  - Lottie / Three.js 接入预留
- **后端与模型链路由 WorkBuddy 负责**
  - 登录 / 注册 / 鉴权链路
  - 语音上传与转写
  - AI 分析真实调用
  - companion / music / analytics 接口联调
  - 日志排查与 fallback 策略收敛

## 2. 五大问题汇总

## 2.1 问题一：未登录首页首屏需要整体重做

### 当前问题

- 当前首页仍带有偏旧版的信息结构。
- 左侧文字块过大，首屏压迫感强。
- `开始体验` 与 `先写下此刻` 语义接近，入口重复。
- 存在 `78.1%` 之类的调查型文案，不适合作为首屏主表达。
- 存在 `今晚` 这类写死时间的文案，不适合长期首页使用。
- 当前 Web 首页角色形象与 iOS 原型图不统一。

### 用户目标

- 首屏只保留一个主按钮：`开始体验`
- 右上角保留 `登录`
- 不要出现 `今晚`、`78.1%` 这类表达
- 不要继续使用左右分栏的大段文案结构
- 首页以动态悬浮形象为主角
- 用户一眼就能看到：
  - MoodWave 是什么
  - 有哪些核心功能
  - 如何开始体验

### 建议方向

- 将首屏改成 **居中式、上下排布** 布局
- 结构控制在：
  - 主视觉动态宠物 / 悬浮球
  - 一句主标题
  - 一句简短说明
  - 一个主 CTA
  - 2-3 个简洁功能点
- 去掉一切“数据证明型”文案
- 去掉“今晚可以怎么开始”这类时间文案

### 角色与动态视觉方向

- 形象以 iOS 三张原型图为基准，统一成同一世界观
- 首页主视觉优先尝试：
  - 第一阶段：静态高质量形象 + 轻动效
  - 第二阶段：Lottie 或轻量 Three.js 悬浮效果

### 宠物 / 角色资产建议

优先方案：

- 使用 `gpt-image-2` 生成原创角色设定图
- 输出内容包括：
  - 正面 / 侧面 / 背面
  - 站立 / 跳动 / 挥手 / 睡觉
  - 开心 / 疑惑 / 提醒 / 安慰等表情
- 角色风格：3D Q 版、软萌、透明背景、适合建模

后续如要升级：

- 可进入 `图片 -> 3D` 流程
- 工具候选：
  - Blender
  - Meshy
  - Tripo
  - Rodin

### 谁更适合负责

- **Codex 适合负责**
  - 首页布局重构
  - 文案收敛
  - 角色主视觉落位
  - Lottie / Three.js 前端接入方案
  - `gpt-image-2` 提示词设计与页面视觉整合
- **WorkBuddy 不适合主负责此问题**
  - 此问题核心是前端信息架构与视觉表达，不是后端能力

## 2.2 问题二：登录页 / 注册页 / 引导页需要统一重做

### 当前问题

- 第三方登录图标错误，尤其微信图标不符合标准样式。
- 左侧视觉形象与首页、iOS 原型不统一。
- 邮箱输入框提示文案不自然，示例型占位符不适合当前风格。
- 登录成功后缺少明确反馈。
- 登录后引导页更像移动端搬运到 Web，底部结构不够自然。

### 用户目标

- 微信图标换成标准绿色微信图标
- 苹果 / 谷歌图标也改成正确品牌图标
- 左侧形象换成与首页统一的悬浮宠物 / 灵音形象
- 邮箱输入框文案改成：`请输入邮箱地址`
- 登录完成后，在页面中上部增加 `登录成功` 提示
- 登录后引导页继续针对 Web 端优化，减少“丑”和“挤”

### 建议方向

- 登录页布局以“左侧主视觉 + 右侧登录框”或“上视觉下登录框”的轻结构为主
- 控制登录页信息密度，避免次要说明过多
- 成功提示采用：
  - 顶部轻 toast
  - 或表单上方成功 banner
- 引导页需重新检查：
  - 滚动区是否过满
  - 页脚区是否过重
  - 分页 / 进度提示是否更适合 Web

### 谁更适合负责

- **Codex 适合负责**
  - 登录 / 注册页视觉和布局重构
  - 图标替换
  - 成功提示交互
  - onboarding Web 化改造
- **WorkBuddy 负责配合**
  - 登录 / 注册接口稳定性
  - 鉴权返回格式
  - 登录成功后的 token / session 行为验证

## 2.3 问题三：登录后首页与灵音伙伴形象体系需要统一升级

### 当前问题

- 登录后首页顶部区块不够自然，卡片感偏重。
- 首页文案偏多，陪伴区与说明区显得挤。
- `重新查看新手引导` 等信息优先级不高，却占用显著位置。
- 当前灵音伙伴形象不是“宠物型伙伴”，风格不统一。
- 灵音伙伴页顶部的形象展示还不够有生命感。

### 用户目标

- 登录后首页更清爽、更治愈，不要堆很多卡片
- 删除低优先级信息，如 `重新查看新手引导`
- 首页文案更短、更自然
- 灵音伙伴形象全面改成宠物型角色
- 候选方向：
  - 小猫
  - 小狗
  - 小鸭子
  - 其他治愈型宠物
- 顶部主形象要支持切换并带有轻微悬浮动态感

### 建议方向

- 登录后首页改成：
  - 顶部一句问候
  - 一个主动作
  - 一个轻量陪伴区
  - 少量次级入口
- 不再堆叠多个并列功能卡
- 灵音伙伴页顶部变成：
  - 当前选中宠物
  - 宠物状态展示
  - 轻微悬浮动效

### 角色生成建议

- 角色图片优先用 `gpt-image-2` 统一生成
- 不继续使用现有奇怪、风格不统一的角色素材
- 形成一整套 Web / iOS 可共用的宠物型伙伴设定

### 谁更适合负责

- **Codex 适合负责**
  - 登录后首页布局重排
  - 伙伴页顶部动态区设计
  - 角色切换体验
  - 角色资产落位
- **WorkBuddy 负责配合**
  - 伙伴配置、角色保存、会话绑定接口
  - 会话/记忆/角色配置的后端一致性

## 2.4 问题四：情绪录入页需要从“多步骤表单”重构为“低负担情绪记录体验”

### 当前问题

当前 Web 版情绪录入页真实实现为严格五步：

- 情绪
- 强度
- 内容
- 标签
- 完成

对应问题如下：

- 步骤切得过碎，用户需要频繁点击 `下一步`
- 标签被放在内容输入之后，顺序不自然
- 补记日期虽然存在，但“当前记录的是哪一天”不够明显
- 日期说明文案偏后台语言
- 日历选中态和弹层层级观感不佳
- 文本输入框 placeholder 不够自然
- 语音转写并非完全缺失，但用户感知非常弱
- AI 分析存在 fallback 路径，用户体感像“假分析”
- 最终结果页缺少可信的处理中间态

### 用户目标

- 不要继续严格用五步式强流程
- 减少点击次数
- 标签更适合和情绪选择放在一起，或前置合并
- 补记日期要更清楚，能明确知道记录的是哪天
- 日历交互与视觉需要更美观
- 输入提示文案更自然
- 录音后用户要能明显看到转写结果
- AI 分析要有真实处理感，不能像模板瞬间生成

### 建议方向

- 参考 iOS 原型，改成“轻分组式”录入结构
- 可考虑拆为：
  - 情绪 + 标签
  - 强度 + 日期
  - 内容 + 图片 + 语音
  - AI 分析确认
- 减少“上一页 / 下一页”强流程感
- 强化日期展示：
  - 明确当前记录归属日
  - 弱化“创建时间”
- 强化语音区反馈：
  - 录音完成后直接露出转写摘要
  - 明确显示识别状态
- 强化 AI 分析中的状态层：
  - 正在整理文字
  - 正在处理语音
  - 正在生成分析

### 前端职责

- **Codex 负责**
  - 录入页信息结构重排
  - 日期区 / 日历组件视觉重构
  - 标签位置调整
  - 语音转写展示优化
  - 分析中间态设计

### 后端职责

- **WorkBuddy 负责**
  - 语音上传与转写接口真实可用性
  - AI 分析接口调用链路
  - fallback 行为收敛
  - 上传失败 / 超时 / 降级策略说明

## 2.5 问题五：音乐页需要从“播放器页”重构为“情绪可视化音乐空间”

### 当前问题

- 页面结构更像播放器页，而不是情绪可视化空间
- 视觉上存在明显的双框感、卡片拼装感
- 可视化区域不够强，不像主角
- AI 陪伴语在异常时直接暴露技术感文案
- 播放进度条的圆点偏大，交互手感不自然
- 整体更像传统音乐产品，不像 MoodWave 的情绪房间

### 用户目标

- 不要做成“网易云音乐那种播放器页”
- 要更像可视化音乐空间
- 布局先做好，为后续真正的可视化效果留空间
- AI 陪伴语文案不要出现技术故障感表达
- 进度条更自然、更轻盈
- 拖动时要更顺手，适合左右快速滑动
- 暂时先以布局和空间感为主，不急着把所有可视化细节做满

### 建议方向

- 页面布局上改成：
  - 主可视化区
  - 轻量控制区
  - 次级播放信息区
- 减少“播放器面板”的存在感
- 给未来波形、粒子、背景、节奏场预留大面积视觉区
- 调整播放条：
  - 降低拇指圆点尺寸
  - 加强横向滑动手感
  - 让整体更像音乐空间中的控制条，而不是通用播放器
- AI 文案统一改成柔和表达

### 参考方向

这一页需要参考两类对象：

- **iOS 原型**
  - 适合提供产品气质和空间层次方向
- **外部可视化音乐网站**
  - 适合参考大画面、波形主导、弱化控件的设计方式

### 谁更适合负责

- **Codex 适合负责**
  - 音乐页布局重构
  - 可视化区留白与层次
  - 播放条样式与交互优化
  - AI 陪伴语前端呈现
- **WorkBuddy 配合**
  - 音乐推荐 / 收藏 / 听后感接口稳定性
  - AI 陪伴语生成接口与 fallback 策略

## 3. 谁适合负责“借鉴网站 / 宠物方案”

## 3.1 借鉴其他网站

更适合由 **Codex** 负责。

原因：

- 这件事核心是页面结构、视觉节奏、控件层级和 Web 端体验判断
- 需要把“参考网站”转译成适合当前项目的前端落地方案
- 不只是收集参考，还要判断哪些元素适合 Web、哪些会带来卡顿或信息过载

Codex 负责内容：

- 首页参考网站调研
- 音乐可视化网站调研
- 对比可借鉴点
- 转换为具体页面布局建议

## 3.2 宠物 / 角色形象方案

分两层：

- **角色设定与页面使用方式**：更适合由 **Codex** 负责
- **最终高一致性资产批量生成**：可由 `gpt-image-2` 或后续专业建模/视觉工具补强

Codex 适合负责：

- 明确宠物角色方向
- 输出 `gpt-image-2` 提示词
- 统一角色在首页 / 登录页 / 伙伴页中的位置和用途
- 决定先上静态图、Lottie 还是 Three.js

如后续进入高质量 3D：

- 可再引入 Blender / Meshy / Tripo / Rodin 流程

## 6. 测试方案

## 6.1 前端测试

每个阶段完成后，Codex 负责执行：

- 首页首屏视觉回归
- 登录 / 注册流程检查
- onboarding 流程检查
- Dashboard 首页排版检查
- 情绪录入交互回归
- 音乐页控制区与布局回归
- companion 角色切换与展示回归

关键断点：

- 390px
- 430px
- 768px
- 1024px
- 1440px

## 6.2 后端测试

每个阶段由 WorkBuddy 负责确认：

- 认证链路
- moods create / list / detail
- AI analyze
- upload voice / image
- companion memories / conversations
- music recommend / favorite / insight

## 6.3 联调测试

联调时重点关注：

- 登录后是否立刻进入正确页面
- 前端是否请求到正确 API 地址
- 补记日期是否正确写入记录
- 语音录入后是否展示转写
- AI 分析是否真实返回
- 音乐页异常文案是否仍暴露技术提示

## 6.4 浏览器回归检查

每轮都检查：

- 强刷后页面是否仍为新版本
- PWA / Service Worker 是否造成旧缓存
- 新旧 worktree / 分支是否混用

## 7. Hook / 提交流程

## 7.1 Git 分支要求

Web 改动统一提交到：

- `codex/web-current`

不要把 Web 改版提交到：

- `codex/ios-capacitor`

## 7.2 提交前 hook

建议沿用当前已补好的 hook / 检查脚本：

- `scripts/check-frontend.sh`
- `scripts/check-backend.sh`
- `scripts/review-web-phase.sh`
- `.githooks/pre-commit`

## 7.3 每阶段提交流程

每个阶段都必须：

1. 跑前端检查
2. 跑后端检查
3. 做一轮浏览器回归
4. 单独 commit
5. push 到 `codex/web-current`

建议 commit 形式：

- `phaseX: <summary>`
- `fix: <specific issue>`

## 8. Code Review 要求

## 8.1 前端 Code Review 重点

- 是否仍然存在信息过载
- 是否出现文案重复
- 首页是否又回到双按钮或左右大分栏
- 登录页 / 引导页是否仍像移动端硬搬
- 角色体系是否统一
- 情绪录入是否还在强依赖“下一步”
- 音乐页是否仍然更像播放器而不是可视化空间

## 8.2 后端 Code Review 重点

- fallback 是否被过度使用
- 语音转写是否真实可见
- AI 分析是否真实执行
- 错误返回是否暴露技术细节给用户
- companion / music / auth 是否有旧逻辑残留

## 8.3 协作审查方式
